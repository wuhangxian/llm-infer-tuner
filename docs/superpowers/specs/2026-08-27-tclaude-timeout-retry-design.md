# tclaude 超时与重试防护设计

## 背景

`gen_configs.sh` 同步等待 `tclaude` 生成候选。网关请求可能保持连接但长期不再返回事件；当前脚本没有超时，因此调用链会无限等待。已有证据表明候选推导、文件读取和流式渲染没有确定性故障，问题属于一次上游请求静默卡住后缺少客户端保护。

## 目标

- 单次 `tclaude` 调用不再无限等待。
- 超时后使用完全相同的模型与参数自动重试一次。
- 第二次仍超时则清晰退出，且不破坏已有正式候选文件。
- 用户主动按 `Ctrl-C` 时快速停止，不自动重试、不遗留子进程。
- 每次尝试分别保留 stdout 和 stderr，便于排障。
- 流式与非流式模式采用一致的超时和重试语义。

## 非目标

- 不自动切换模型或网关。
- 不实现基于输出活跃度的空闲超时。
- 不修改候选生成 prompt、JSON Schema 或候选解析规则。
- 不重试鉴权失败、参数错误、渲染失败等普通非零退出；本次只处理确认出现过的超时故障。

## 方案与边界

新增 `runners/tclaude_guard.py`，作为 `gen_configs.sh` 与 `tclaude` 之间的小型进程监督器。使用 Python 而不是继续扩充 Bash 管道，是为了把进程组、并发读取 stdout/stderr、信号转发和原子状态记录收敛在一个可独立测试的边界内。

guard 的职责：

1. 校验超时、宽限期和重试次数。
2. 每次尝试用 `start_new_session=True` 启动新的 `tclaude` 进程组。
3. 并发读取 stdout/stderr，分别实时落盘，避免管道缓冲死锁。
4. 流式模式把 stdout 同步转发给父进程，供现有 `jq` 进度渲染；非流式模式不转发。
5. 到达软截止时间后向整个进程组发送 `TERM`；宽限期结束仍未退出则向整个进程组发送 `KILL`。
6. 只有 guard 自己触发的软超时或强杀才归一为退出码 `124`，并可重试。外部信号或普通进程退出不会被误判为超时。
7. 收到 `SIGINT` 时立即标记用户中断，向当前子进程组发送 `INT`；等待 1 秒后仍存活则发送 `TERM`，再等待 2 秒仍存活则发送 `KILL`。首次中断后的硬退出上限为 4 秒（包含调度余量），最终返回 `130`，且绝不重试。清理期间再次收到 `SIGINT` 时立即向子进程组发送 `KILL`。
8. 成功时原子写入一个 success-path 状态文件，告诉 Shell 应解析哪次尝试的 raw 文件。
9. 收到外部 `SIGTERM` 或 `SIGHUP` 时采用 `TERM → 2 秒 → KILL` 清理子进程组，分别返回 `143` 或 `129`，不重试。
10. 普通子进程若自行被信号终止，Python 的负返回码统一映射为 `128 + signal`；只有 guard 已记录“本次由 deadline 触发”的 TERM/KILL 才归一为 `124`。
11. raw 文件或 success-path 状态文件创建、写入失败属于 guard 普通错误：返回 `1`、不重试且不得写 success-path。

`gen_configs.sh` 的职责：

1. 组装原有 prompt 和 `tclaude` 参数。
2. 调用 guard；流式模式仅将 guard stdout 接到进度 `jq`，不再由外层 `tee` 管理 raw。
3. 在读取其他状态前立即保存完整 `PIPESTATUS`。guard 非零优先作为调用失败；guard 成功但渲染器失败时，按渲染错误退出。
4. 从 success-path 状态文件读取成功尝试的 raw 文件，执行现有候选解析。
5. 候选先写入输出目录内的临时文件，解析成功后用 `mv` 原子替换正式输出。
6. 使用 `EXIT` trap 清理状态文件和未提交的输出临时文件；`INT` trap 统一退出 `130`。

## 用户接口

- `GEN_TIMEOUT_SECONDS`：软截止时间，默认 `600` 秒，必须是 1–86400 的十进制整数。
- `GEN_TIMEOUT_GRACE_SECONDS`：软截止后的 TERM 宽限期，默认 `10` 秒，必须是 1–300 的十进制整数。
- `GEN_MAX_RETRIES`：超时后的重试次数，默认 `1`，必须是 0–10 的十进制整数。

因此默认单次尝试的完整墙钟硬上限约为 `610` 秒，最多执行两次。启动信息同时打印软超时、强杀宽限期和最大尝试次数。

示例：

```bash
GEN_TIMEOUT_SECONDS=900 ./gen_configs.sh input/jobs/example.json
GEN_MAX_RETRIES=0 ./gen_configs.sh input/jobs/example.json
```

配置值使用正则校验后再做十进制转换，避免 `08` 被 Bash 当成八进制。

## 状态机

```text
开始尝试（全新 tclaude 会话与进程组）
  ├─ rc=0 ───────────────────→ 记录 success-path → Shell 原子解析/提交候选
  ├─ guard 触发超时且可重试 ─→ 清理进程组 → 提示 → 同参数下一次尝试
  ├─ guard 触发超时且次数用尽 → 清理进程组 → 退出 124
  ├─ 收到 SIGINT ────────────→ 清理进程组 → 退出 130，不重试
  └─ 其他非零/信号退出 ──────→ 清理进程组 → 透传或映射退出码，不重试
```

若第一次超时、第二次普通失败，最终透传第二次的普通失败码；只有最后一次也是 guard 判定的超时才返回 `124`。

## Raw 文件与正式输出

每次脚本运行生成不会碰撞的运行 ID（UTC 时间、父 PID 与随机后缀），每次尝试写：

```text
claude-raw-outputs/<job_id>.<run_id>.attempt-1.stdout.jsonl
claude-raw-outputs/<job_id>.<run_id>.attempt-1.stderr.log
claude-raw-outputs/<job_id>.<run_id>.attempt-2.stdout.jsonl
claude-raw-outputs/<job_id>.<run_id>.attempt-2.stderr.log
```

非流式 stdout 使用 `.json` 后缀。失败输出不会覆盖其他运行，也不会遗留含义不明的 stale attempt 文件；错误信息列出本次运行的 attempt 路径。即使非流式调用超时，已经收到的部分 stdout/stderr 也会留在对应文件中。

正式输出采用事务语义：

- 解析写入与 `OUT` 同目录的临时文件。
- 完整校验成功后才原子 `mv` 到 `OUT`。
- 超时、普通错误、解析错误和中断都清理临时文件。
- 若运行前已有 `OUT`，失败时原样保留，并明确打印“已有输出未修改”；不会删除用户此前的有效结果，也不会把半文件暴露为新结果。

总超时而非空闲超时是刻意选择：模型在工具调用或推导阶段可能合法地数分钟没有文本输出，空闲超时容易误杀。600 秒高于当前常见的 2–6 分钟耗时，同时为网关静默卡住提供确定上限。

## 测试设计

### guard 单元/集成测试

使用真实子进程与短测试超时验证：

1. 正常命令只执行一次，stdout/stderr 分别落盘，success-path 指向成功 raw。
2. 第一次软超时、第二次成功；两次 argv（尤其 `--model`）完全相同，无 fallback。
3. 两次软超时后退出 `124`。
4. fake 进程忽略 `TERM` 并派生子进程；guard 升级 `KILL`、按超时重试，结束后父子进程均不存在。
5. 测试向 guard 真实发送 `SIGINT`；快速退出 `130`、不发生第二次调用、无遗留父子进程。
6. 普通非零退出透传且不重试。
7. 子进程自行被信号终止时映射为 `128 + signal`，且不重试。
8. `SIGTERM`/`SIGHUP` 清理子进程组并返回对应 shell 状态码。
9. 非法数字、前导零和越界配置在启动子进程前失败。
10. raw/state 写入失败不重试、不产生 success-path。
11. 首次超时的部分 stdout/stderr 与第二次成功输出分别保留，success-path 只指向成功尝试。
12. stdout 消费端提前关闭时，guard 清理子进程并返回非成功状态。

### gen_configs 入口测试

继续通过公开入口运行脚本，验证：

1. 流式和非流式模式各自覆盖“首次超时后成功”和“两次超时”。
2. 正常成功路径保持默认 HY3、模型命令行覆盖和既有候选解析行为。
3. 非法环境配置在调用 `tclaude` 前失败。
4. 首次超时的 partial raw 被保留，最终只解析成功尝试。
5. 运行前已有正式输出时，超时或解析失败后内容不变。
6. 模拟解析失败，断言正式输出不出现、同目录临时文件被清理。
7. 模拟进度渲染器失败，断言脚本非零退出且不提交正式输出。
8. 每次尝试的 stdout/stderr 文件一一对应。
9. 将 `gen_configs.sh` 作为独立前台进程组启动，fake `tclaude` 阻塞并派生子进程；向整个前台进程组发送一次 `SIGINT`，断言 4 秒内返回 `130`、只调用一次、正式输出保持原样，Shell、guard、fake tclaude 和派生子进程均退出。

另在解析阶段向脚本发送 `SIGINT` 验证输出临时文件 trap。渲染失败测试同时断言 `tclaude` 只调用一次，证明渲染故障不会触发模型重试。
